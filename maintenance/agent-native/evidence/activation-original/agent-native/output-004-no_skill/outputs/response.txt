### Part 1: Diagnosis & Distinction of Causes vs. Framework Behavior

#### Likely Causes (Hypotheses)
1. **Broken Module Import Paths:** A new page attempts to import `useNavigationState` from a Core package instead of the local app hook (`app/hooks/use-navigation-state.ts`), leading to fragmented navigation state and uncoordinated tab IDs.
2. **Missing Actor/Context Validation:** The view-screen action blindly loads any supplied record ID without verifying the current actor or project context, causing stale selection carry-over (Project A's ID persisting in Project B).
3. **Mismatched Cache Keys:** UI mutations update the database, but raw queries using custom/hardcoded cache keys fail to invalidate or update, meaning data changes only appear after a full page reload.
4. **Aggressive Unconditional Polling:** A newly added global timer refetches *every* query every second, ignoring whether the screen is active or static (e.g., settings pages).
5. **Decentralized Tab/Navigation Polling:** Each component generating its own tab ID and polling navigation commands independently causes race conditions, double-navigations, and UI jitter when writing selections.

#### Verified Framework Behavior (Directly from Observations)
* **Stale State persistence:** Navigation from Project A to Project B leaves the agent with A's selected record ID.
* **Cache isolation failure:** Raw queries with custom cache keys do not automatically sync with database mutations.
* **Global refetch overhead:** Timers executing per-second refetches impact static settings pages unnecessarily.
* **Concurrency conflicts:** Component-level tab ID generation and independent polling directly result in duplicate navigation commands and visible rendering jitter.

### Part 2: Ordered Repair Sequence

Distinguish carefully between **UI actions**, **local agent-run refreshes**, and **remote updates** during the repair:

1. **Step 1: Fix Navigation Source of Truth (UI Actions & Local State)**
   * *Action:* Correct the import on the new page to use the local app hook (`app/hooks/use-navigation-state.ts`) rather than the Core import.
   * *Action:* Centralize tab ID generation and navigation command polling to a single provider or root layout instead of letting every component create its own tab ID. This eliminates duplicate navigation commands and selection jitter.

2. **Step 2: Secure Context Switch & Record Loading (UI Actions)**
   * *Action:* Update the view-screen action to validate the current actor and project context against the requested record ID before loading data. If the record belongs to Project A and the user is in Project B, reject or reset the selection immediately upon navigation.

3. **Step 3: Align Cache Invalidation (Local Agent-Run Refreshes)**
   * *Action:* Audit raw queries with custom cache keys. Ensure that UI and agent-driven mutations explicitly invalidate or update those specific cache keys so changes render immediately without requiring a full page reload.

4. **Step 4: Optimize Polling and Scopo-Targeted Refetches (Remote Updates & Static Pages)**
   * *Action:* Remove the global 1-second timer refetching *all* queries. 
   * *Action:* Implement targeted polling or real-time subscriptions *only* where required (e.g., the shared project list that must show edits from a second user). 
   * *Action:* Explicitly exempt static settings pages from remote-update polling and background refetches.
